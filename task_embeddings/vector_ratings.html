Vector Ratings

A skill-modelling framework for sheaf that generalizes scalar Elo to a high-dimensional space. Direction encodes what you are good at, magnitude encodes how good you are.

Classical Elo gives every player and every problem one number; this does not generalize well to tasks of varying type: a player can be strong at combinatorics and weak at calculus, and a single scalar cannot express this. So both sides of a game become geometric objects:

  • A player's strengths are represented by a skill_vector; direction encodes skill composition (what types of problems they are good at), length encodes strength.
  • A problem is a unit vector, the task_direction, plus a scalar difficulty. The direction says what the problem is about; the scalar says how hard it is.

The task_direction comes from a text-embedding model run over the problem statement (see embeddings_writeup.html for which model and why). Semantically similar problems point in similar directions; playing one problem teaches the system something about your strength on nearby problems, for free.

1. Classical Elo derivation

Classical Elo is a reparameterization of the Bradley-Terry Model, so we start with that. Give each side a positive number measuring playing strength: strength_a, strength_b, and model the win probability as a share of the total strength:

P(a beats b) = strength_a / (strength_a + strength_b)

P ∈ (0, 1), equal strengths give 0.5, and only the ratio matters — doubling both numbers changes nothing. Since only ratios matter, we can take logarithms. Every positive number is an exponential, so we define:

rating_a = ln(strength_a) rating_b = ln(strength_b)

Thus:

P = e^rating_a / (e^rating_a + e^rating_b) = 1 / (1 + e^(rating_b - rating_a)) = 1 / (1 + e^-(rating_a - rating_b)) = logistic(rating_a - rating_b)

The win probability now depends only on the difference of log-strengths. Equal rating differences mean equal win probabilities at every level of play, which is exactly why ratings live on an additive scale.

Score a win as 1 and a loss as 0; then the sigmoid's output is the expected score: 1 * P(win) + 0 * P(loss). After the game, move the rating toward the observation, in proportion to the prediction error scaled by learning_rate (Elo's K-factor):

new_rating = rating + learning_rate * (outcome - expected_score)

2. Vector ratings

A scalar rating assumes a single axis of ability; the vector model drops this assumption. Section 1's rating difference becomes the difference between the player's projected strength on the task and the problem's difficulty; everything else carries over unchanged.

Player vs problem (the sheaf game mode)

The opponent is the problem itself, whose "skill" is its scalar difficulty:

strength = skill_vector · task_direction expected_score = logistic(strength - difficulty)

The player and the problem both update from the same prediction error:

Δskill_vector = learning_rate * (outcome - expected_score) * task_direction Δdifficulty = -learning_rate * (outcome - expected_score)

Toy example

task_direction = (0.8, 0.6, 0) # unit length: 0.8² + 0.6² = 1 difficulty = 1.3 skill_vector = (1.2, 0.3, 0.2) learning_rate = 1 strength = 1.2*0.8 + 0.3*0.6 + 0.2*0 = 1.14 expected_score = logistic(1.14 - 1.3) ≈ 0.460

The player wins (outcome = 1). The prediction error is 1 - 0.460 = 0.540:

Δdifficulty = -0.540 Δskill_vector = 0.540 * (0.8, 0.6, 0) = (0.432, 0.324, 0) difficulty → 0.760 skill_vector → (1.632, 0.624, 0.2) # check: new strength = 1.632*0.8 + 0.624*0.6 = 1.680 = 1.14 + 0.540 ✓ # check: Δstrength + Δdifficulty = 0.540 - 0.540 = 0 ✓

The player's skill grew only along this problem's direction, and the problem got easier by exactly the amount the player got stronger.

Over multiple games

skill_vector is a weighted sum of the directions of everything the player has played, weighted by how surprising each result was:

skill_vector = Σ over games i: learning_rate * (outcomeᵢ - expectedᵢ) * task_directionᵢ

3. High-dimensional geometry: what the update actually does

Everything about cross-task interaction reduces to one linear object. Stack the played task_directions into a matrix M (dimension_count rows, one column per game) and let C = MᵀM be the cosine matrix between them. The skill vector is the initial vector plus a weighted sum of played directions, and strength on every task is:

skill_vector = skill_vector₀ + M·w # w = per-game updates, lr·(outcome - expected) strength(task) = skill_vector · task_direction = (C·w)_task

Training task t changes strength at task u by exactly learning_rate · C_tu — the cosine between the two directions. Negative transfer (improving at one task scores as decline at another) happens precisely where the cosine matrix has negative entries, with magnitude equal to that cosine. The sign structure of C is the model's theory of transfer.

Two tasks: common vs difference axis

For tasks A, B with cos θ = c, decompose their directions into a common axis m ∥ d_A + d_B and a difference axis n ∥ d_A - d_B — orthogonal by construction. Alternating wins on A and B give:

per A,B cycle: +2·lr·cos(θ/2) along m, 0 along n strength at A: +lr·(1 + c) per cycle, swinging by lr·|c| game to game

At exact opposition (c = -1) the model credits nothing: strength at A oscillates by learning_rate every game and never grows, no matter how many games are won. The shared skill — the component that would help both A and B — is learned at rate (1 + c)/2, zero when the tasks point against each other. The difference axis nets zero only for symmetric wins; asymmetric outcomes (win at A, lose at B) accumulate it, which is the model correctly recording specialization. The failure is specific: a player who genuinely improves at both sides of an opposed pair gets no skill credit at all.

Random directions: high dimension is the safe regime

If task directions were independent and uniform over the unit sphere, the cosine of a random pair has mean 0 and variance 1/dimension_count; typical |cosine| ≈ 0.798/√dimension_count, and P(cosine ≤ -c) ≈ Φ(-c·√dimension_count). Anti-alignment decays exponentially with dimension: at 384 dims a pair as anti-aligned as -0.2 occurs with probability ~3e-5, and even the single most anti-aligned pair in a 100k-problem corpus is only ≈ -0.35 by chance. Random directions tend to orthogonality as dimension grows — exactly the "change along A changes nothing along B" limit. High dimension destroys spurious anti-alignment; it is not the source of the pathology. (And the skill vector is not "sparse": embeddings are dense, so every update moves every coordinate.)

Mean-centering pins the mean: the -1/(N-1) identity

0 = ‖Σ u_i‖² = N + 2·Σ_{i<j} cos(u_i, u_j) → mean pairwise cosine = -1/(N-1)

Mean-centered unit vectors satisfy this constraint exactly. The measured -0.143 after centering the 8-problem corpus is -1/7 — a finite-sample identity, not evidence that centering creates anti-alignment. At corpus scale (N ≈ 100k) the centered mean pairwise cosine is ≈ 0: typical pairs are near-orthogonal, precisely the zero-mean assumption the spread formula needs.

Structured corpora: the pathology is set by domain count, not dimension

Real corpora are not uniform — they cluster by topic, and clustering survives high dimension. After centering, K balanced domains have centers forming a regular simplex: cross-domain cosines ≈ -1/(K-1), identical at any dimension (measured -0.92, -0.46, -0.31, -0.13 for K = 2, 3, 4, 8 at both 32 and 1024 dims). Two domains become near-exact opposites; ten dilute the anti-alignment to -0.1.

The oscillation pathology is a low-domain-count phenomenon, not a high-dimensional one. A two-domain corpus ("math vs humanities") after mean-centering puts the domains almost exactly opposite. Training both yields near-zero skill credit; training one is scored as active decline in the other. The knob that controls the pathology is the number of effective domains K, not dimension_count.

Consequences for the rating system

  • Predictions at played tasks stay correct anyway. Difficulty absorbs the improvement: expected scores still converge to 1 while the skill vector stays at zero. The distortion shows up where the skill vector is actually used — cross-task prediction and player-vs-player ranking.
  • Unplayed tasks never move. The skill vector lives in the span of the played directions (rank at most one per game, whatever the ambient width), so mastery of unplayed topics is unrepresentable by construction; the orthogonal component stays exactly zero.
  • Centered strengths are zero-sum over the corpus. Skill is relative, not absolute: "good at X relative to a typical problem" implies below-average strength somewhere else. This is comparative advantage as geometry — a modeling choice, not a fact about the world. It is the right object for matchmaking (which only ever compares), and the wrong object if a strength drop on an unplayed topic is read as "the player got worse at it".

4. Real embedding geometry: anisotropy and the fix

A first-pass derivation gives the spread of a player's strength over randomly chosen tasks as:

sd(skill_vector · task_direction) = ‖skill_vector‖ / √dimension_count

This is exact if task directions are distributed uniformly over the unit sphere — i.e., if a random problem's direction is as likely to point one way as any other. Baked into a matchmaking tolerance, that assumption looks like:

tolerance = 0.8416 * ‖skill_vector‖ / √1536 # 0.8416 = Φ⁻¹(0.80), the normal quantile
The assumption is false. Real text embeddings are anisotropic: the whole cloud occupies a narrow cone, not the sphere. Measured on a handful of deliberately-unrelated STEM problems (all-MiniLM-L6-v2, see embeddings_writeup.html §5), the mean pairwise cosine between different problems was +0.094 (embedding_geometry.ipynb §2) where uniformity predicts 0 — and that was on a corpus designed to be diverse. A real all-STEM corpus sits much deeper in the cone (0.3-0.6 typical). Consequences:
  • strength = skill_vector · task_direction is not zero-mean over tasks — it's shifted positive, so "average" performance is misread as "good".
  • The sd formula understates the spread; tolerance windows computed from it are miscalibrated.
  • Cross-topic transfer is systematically larger than the model intends (everything correlates with everything).
Fix: mean-center the embedding cloud. Compute the corpus mean direction μ over all problem embeddings, subtract it from every problem's vector, and renormalize to unit length. Then "task direction" means "direction away from the average problem" — a much better skill axis ("good at X relative to a typical problem") — and the zero mean assumed by the spread formula is approximately restored. In the measurement cited above, mean-centering moved the mean pairwise cosine from +0.094 to -0.143 — and -0.143 is exactly -1/(N-1) for the 8-problem sample (§3): centering pins the mean pairwise cosine to -1/(N-1), a finite-sample identity, so the drop is the identity doing its job, not evidence that the corpus became anti-aligned. At corpus scale that mean is ≈ 0 and typical pairs are near-orthogonal — precisely the zero-mean assumption the spread formula needs. Recompute μ whenever problems are bulk-imported; store it alongside the vectors.

Note what the fix buys and costs. Centered strengths are zero-sum over the corpus (§3): the skill vector is a redistribution operator, and absolute improvement is unrepresentable in it — difficulty carries that instead. For matchmaking, which only ever compares players and problems on the same scale, relative skill is the right object; don't read a strength drop on an unplayed topic as "the player got worse at it" — that is the geometry speaking, not evidence.

5. Cold start

Two separate cold starts need handling:

New player: skill_vector = 0

Then strength = 0 on every task and ‖skill_vector‖ = 0, so the tolerance window collapses to a point — the matchmaking band is exactly difficulty ≈ 0. A tempting patch — hardcoding a wide band like [-10, 10] for everyone — defeats the point of matchmaking. The real fix is an exploration phase: for the first N games, sample problems near the global median difficulty (or uniformly), ignoring the tolerance band, and widen the band smoothly as ‖skill_vector‖ grows from 0. The band formula itself handles the widening once the mean/calibration is right — the problem was only ever the zero vector.

New problem: difficulty is a guess

A problem's difficulty only converges after many attempts (each attempt moves it by at most learning_rate * ½). Seed new problems from their embedding neighborhood: initialize difficulty to the difficulty-weighted average of its nearest few existing problems, then let play refine it. This also makes new problems immediately matchable instead of invisible.

6. Calibrate the matchmaking band empirically

The matchmaking flow: the player's search query is embedded into a query direction; the player's strength is computed against that direction; problems are fetched near the query direction with difficulty inside [strength - tolerance, strength + tolerance], where tolerance targets an 80%/20% win-probability window.

Keep the flow, replace the constant:

  • Do not compute tolerance as 0.8416 * ‖skill_vector‖ / √dimension_count. That derivation assumes isotropic directions (section 4) and a normal strength distribution (unverified).
  • Instead, measure: over the real corpus, compute the distribution of skill_vector · task_direction for the player, and set the band from its empirical quantiles. One extra SQL query over the problems table; no distributional assumptions at all.
  • Recheck the band against realized win rates periodically. If players inside the band win 60% rather than ~50%, widen it; the sigmoid and the band are estimates, the win rate is ground truth.

7. The embedding model is part of the rating state

If you swap or fine-tune the embedding model, every stored skill vector silently changes meaning: the new model's task directions live in a different space, so skill_vector · task_direction_new is noise. Ratings are only valid under the embedding model that produced the task directions.
  • Pin model name + version + dimension count + mean-centering vector version alongside every stored vector. problems.version exists; player skill rows need the same.
  • A model upgrade is a migration: re-embed all problems, recompute μ, and either rescale/archive existing skill vectors or map them through the old→new direction correspondence (lossy; prefer archive + exploration phase, as in cold start).
  • This coupling is the argument for keeping search and skill vectors as separate columns even when they come from the same model: you can retune the search side (truncation, centering, hybrid weights) without touching rating history, as long as the skill projection is frozen.

9. Properties summary

  • One rule, one mode. The player-vs-problem game: the problem is an opponent whose skill lives on one scalar axis.
  • Reduces to Elo at dimension_count = 1. Nothing special-cased.
  • Zero-sum conservation along the task direction — rating inflation is structurally contained.
  • Skill is relative, not absolute. Mean-centered strengths are zero-sum over the corpus; absolute improvement is absorbed by difficulty and unplayed topics are invisible (§3, §4).
  • Transfer for free: no per-topic rating tables to maintain; generalization falls out of embedding geometry.
  • Difficulty is learned from the population rather than authored, and problems and players are calibrated on the same scale by construction.
