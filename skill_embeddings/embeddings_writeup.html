Embedding Models

What an embedding actually is, how model size and dimensionality affect quality, and how to build search that doesn't return unrelated bullshit. Written for sheaf's use case: short English STEM problem statements, thousands (not millions) of rows, Go + SQLite monolith.

TL;DR for sheaf. Qwen3-Embedding-0.6B via Ollama (Apache-2.0, 1024 dims, Matryoshka-truncatable, 32K context, runs on CPU). Embed title + statement per problem, store float32 blobs + model version in SQLite (sqlite-vec), brute-force scan — milliseconds at this scale. Search: vector top-30 ∪ FTS5 top-30, merge with RRF, add a cross-encoder reranker when users complain. Thresholds: calibrate on your own corpus, there is no universal number. Build a 50-query eval set from the searches table before tuning anything.

1. What an embedding actually is

The naive picture — "the narrowest bottleneck layer at the far right of the network diagram" — is half right, and the wrong half is the important one.

Right half: you do run text through the network and read off one fixed-size vector near the output. For encoder models (BERT-family: MiniLM, BGE, E5) the top layer produces one hidden vector per token; a pooling step (mean over tokens, or the [CLS] token) collapses them into one vector. For the modern decoder-LLM embedders (Qwen3-Embedding, gte-Qwen2) you take the last token's hidden state instead.

input tokens
→
transformer blocks × N
→
final hidden states
(one vector per token)
→
pooling
(mean / [CLS] / last-token)
→
embedding vector

Wrong half: it is usually not a bottleneck — the embedding is the full hidden width (768, 1024, 4096), nothing narrows. And the tap location is not what makes it an embedding. What makes it one is the training objective: contrastive learning (InfoNCE) over hundreds of millions of (query, relevant-passage, hard-negative) triples, which sculpts the space so that cosine similarity means semantic relevance. Same transformer without that training → useless geometry: raw BERT mean-pooled vectors lose to 2014-era GloVe on similarity tasks, which is exactly the result that motivated sentence-transformers. You are buying the training, not the architecture.

Consequences that fall out of "the geometry is trained":

  • Vectors from two different models are never comparable — different spaces, different planets. Never mix models (or versions, or truncations) inside one index.
  • Models trained for asymmetric retrieval (short query → long document) expect you to mark which is which — prefixes or instructions (§4). Using one side's format for the other costs real accuracy.
  • Vector arithmetic (embed(a) − embed(b)) is not principled in these spaces. Contrastive embeddings are not word2vec; directions don't decompose into concepts you can subtract.

Within the Qwen3 family, 0.6B → 8B is 13× the compute for ~4.5 points. Where size genuinely pays, per an independent 2026 benchmark (10 models, tasks MTEB doesn't cover):

  • Long documents. Sub-335M models collapse past ~4K characters: 0.4–0.6 accuracy on needle-in-a-haystack at 8K chars, where ≥2B models score ~1.0. Sheaf verdict: irrelevant — problem statements are short.
  • Cross-lingual. English-only small models score 0.12–0.15 R@1 on Chinese↔English retrieval (functionally zero). Sheaf verdict: irrelevant unless you go multilingual; then look at bge-m3.
  • Hard negatives / instruction following. Bigger models distinguish "kinetics, NOT energy methods" better. Mildly relevant for sheaf queries with exclusions — but handle exclusions with SQL filters and reranking anyway (§4).
Three leaderboard traps. (1) MTEB scores are only comparable within the same board version — v2 numbers and the old 56-task numbers are different scales. (2) Several toppers are non-commercial licensed: NV-Embed-v2 and jina-embeddings-v3 are CC-BY-NC — fine for experiments, not for a product. (3) MTEB rank ≠ rank on your corpus; LaTeX-flavored STEM text is a niche. The only leaderboard that matters is the eval set you build yourself (§4).

3. Dimensionality

Dimension count is capacity, not quality. A 1024-dim Qwen3-0.6B beats old 1536-dim models; a 384-dim MiniLM loses to 1024-dim BGE not because 384 < 1024 but because the model is weaker. What dims actually cost:

  • Storage/compute: 4 bytes × dims per float32 vector. 1024 dims × 100k problems = 400 MB. Dot products scale linearly. Irrelevant at sheaf scale; matters past ~millions of vectors.
  • Effective dimensionality is low. Embedding clouds are low-rank. Measured on the demo corpus: 6 of 384 principal components carried 90% of the variance (toy scale, but the effect is well documented). Nominal dims ≫ information dims.

MRL: pick the dimension after embedding

Models trained with Matryoshka Representation Learning (Qwen3-Embedding, nomic-embed-text-v1.5, jina-v3, OpenAI text-embedding-3-*) have the property that the first N coordinates of the vector form a valid smaller embedding. Independent measurement: truncating to 256 dims costs <1% Spearman correlation for MRL-trained models. So the workflow is: embed once at native size → truncate → renormalize → store. (Without MRL training it still "sort of" works on easy corpora — MiniLM 384→64 preserved top-3 ranking in the demo — but don't rely on it.)

For sheaf specifically, d has a second job: it's also the dimension of the skill space in the rating system, where smaller is better (convergence, per-axis statistics). Plan: 1024-dim vectors for search, a 256-dim MRL-truncated + mean-centered projection for skill. See vector_ratings.html §7.

4. Search quality: the model is 40% of it

The rest is pipeline. All findings below are from live runs on this machine (all-MiniLM-L6-v2, CPU; scripts and outputs in §7).

Finding 1: ranking works; absolute scores don't

query "related rates ladder sliding down a wall"  →  correct problem 0.719, next best 0.264
query "how to diagonalize a symmetric matrix"     →  correct problem 0.584, next best 0.134

Embedding search is a ranking device. The margins on relevant results are wide. But the absolute numbers mean nothing in isolation:

nonsense query "best recipe for chocolate chip cookies", max cosine over corpus:
corpus    8 docs: +0.057
corpus   32 docs: +0.290   ← top hit: "A recipe for heat with energy: timing, temperature…"

There is no universal similarity threshold. "0.5 means relevant" is folklore; scores are uncalibrated and depend on the model, the corpus, and the query. Any threshold must be measured on your data (below).

  1. Use the model's query/document asymmetry. E5 wants "query: " / "passage: " prefixes; BGE wants an instruction sentence prepended to queries; Qwen3-Embedding accepts a free-text instruction like "Find a STEM practice problem about: …". Skipping this costs measurable points. It also replaces attempt-3's query-rewrite hack: instruction-tuned embedders give you "emphasize X" behavior natively. Hard exclusions ("NOT differential equations") belong in SQL WHERE clauses or the reranker prompt, never in vector arithmetic.
  2. Hybrid with keyword search. Embeddings systematically miss exact tokens. You're on SQLite: FTS5 is built in. Merge with RRF.
  3. Rerank. Bi-encoders score query and document separately (fast, fuzzy); cross-encoders see them together and are dramatically better at precision. Cheap: only 20–50 candidates cross the reranker. This is the standard answer to "unrelated bullshit in the top-k".
  4. Threshold by calibration, not folklore. Embed your real problems, run real queries, look at the score distributions for results you judge good vs bad, pick a cutoff. Or sidestep absolute scores: require top-1 to clear the field by a margin.
  5. Build the eval harness first. 30–100 (query → known-relevant problem) pairs, measure recall@5 / MRR, rerun after every model/dim/pipeline change. Without it, every choice in §§2–3 is vibes. Sheaf already logs every query to the searches table — that table is the future eval set, and later a source of implicit relevance labels (which problem did the user actually play).

5. Geometry quirks that matter for sheaf

Covered fully in vector_ratings.html §6 — the short version, since it's an embedding fact, not a rating fact:

  • Anisotropy: embedding clouds occupy a cone, not the sphere. Measured on 8 deliberately diverse STEM problems: mean pairwise cosine +0.094 (uniformity predicts 0); same-domain corpora run 0.3–0.6. Any math that assumes zero-mean random directions (like the rating system's tolerance formula) is miscalibrated until you mean-center the corpus (subtract the mean embedding μ, renormalize; measured effect: +0.094 → −0.143).
  • Truncation interacts with search and skill differently — search tolerates high d, skill wants low d. Two projections of one frozen model is fine; two models is not.

6. Operations on the Go + SQLite monolith

  • Inference: ollama pull qwen3-embedding:0.6b, call its HTTP API from Go. Boring, swappable, runs on CPU at sheaf's QPS. (Alternative: ONNX runtime in-process via fastembed-style bindings — more setup, same result.)
  • Storage: float32 blobs via the sqlite-vec extension. Brute-force scan is single-digit milliseconds at thousands of vectors; you don't need an ANN index (HNSW) until ~100k+. Attempt-3 had no vector index on pgvector and serialized vectors as text strings (toSql()) — do neither.
  • Versioning: store model_name, model_version, dims with every vector. The embedding space freezes at index time; a model swap = re-embed everything. For the skill vectors this is not just ops hygiene — it invalidates ratings (vector_ratings.html §10).
  • Quantization (later): int8 or binary cuts storage 4–32× with small quality loss. Irrelevant until scale.
  • Free feature: the same index gives duplicate detection for user-authored problems — cosine > ~0.95 flags a likely dupe before insert.
