Vector Ratings

A skill-modelling framework for sheaf that generalizes scalar Elo to a high-dimensional space. Direction encodes what you are good at; magnitude encodes how good you are.

This is the HTML edition of old-garbage/attempt-3/RatingSystem/rating_system.tex, with two changes: variable names are written out in words (no single letters to forget), and it includes everything attempt-3 learned the hard way about applying the model on top of real embedding geometry — anisotropy, mean-centering, dimensionality choice, cold start, and calibration. Sections 2–4 are the original model; sections 5–9 are the corrections.

1. Overview

Classical Elo gives every player one number and every problem one number. Sheaf wants more: a player can be strong at combinatorics and weak at calculus, and a scalar can't say that. So both sides of a game become geometric objects:

  • A player is a vector — the skill_vector. Its direction is the player's skill composition (which kinds of problems they are good at); its length is overall strength.
  • A problem is a unit vector — the task_direction — plus a scalar difficulty. The direction says what the problem is about; the scalar says how hard it is.

The task_direction comes from a text-embedding model run over the problem statement (see embeddings_writeup.html for which model and why). Semantically similar problems point in similar directions, which is exactly what gives the system its power: playing one problem teaches the system something about your strength on nearby problems, for free.

At dimension_count = 1 every vector collapses to a scalar and the whole framework reduces to ordinary Elo. Nothing new is needed for that case — it falls out.

The sigmoid squashes a strength difference into a win probability:

sigmoid(x) = 1 / (1 + e^(−x))

3. Player vs player (both players on the same task)

Each player's scalar strength on this task is the projection of their skill vector onto the task direction:

strength_a = skill_vector_a · task_direction strength_b = skill_vector_b · task_direction

The expected outcome for player A is the sigmoid of the strength difference (a Bradley–Terry model):

expected_score_a = sigmoid(strength_a − strength_b)

After the game, both skill vectors move along the task direction by an amount proportional to the prediction error:

Δskill_vector_a = learning_rate × (outcome_a − expected_score_a) × task_direction Δskill_vector_b = −Δskill_vector_a

The updates are antisymmetric — whatever skill mass A gains along this direction, B loses:

Δskill_vector_a + Δskill_vector_b = 0 (zero-sum, like Elo)

Note what the geometry buys you: only the task-relevant components of each player's skill move. Losing a combinatorics game barely dents your calculus skill, because the update vector points along the combinatorics direction — except insofar as the two topics are correlated in embedding space (section 6).

4. Player vs problem (the sheaf game mode)

Same shape, but the opponent is the problem itself, whose "skill" is its scalar difficulty:

strength = skill_vector · task_direction expected_score = sigmoid(strength − difficulty)

Both sides update from the same prediction error:

Δskill_vector = learning_rate × (outcome − expected_score) × task_direction Δdifficulty = −learning_rate × (outcome − expected_score)

Again antisymmetric, conserving "skill mass" along the task direction:

Δstrength + Δdifficulty = 0

A problem that players keep beating gets easier (difficulty drifts down); a problem that keeps beating players gets harder. Difficulty is therefore learned from the player population, not authored — but it only converges once enough players have attempted the problem (section 8, cold start).

Worked example

A 3-dimensional toy. Unit task direction, a mid-strength player, a problem slightly too hard for them:

task_direction = (0.8, 0.6, 0) # unit length: 0.8² + 0.6² = 1 skill_vector = (1.0, 0.5, 0.2) difficulty = 1.3 learning_rate = 1 strength = 1.0×0.8 + 0.5×0.6 + 0.2×0 = 1.1 expected_score = sigmoid(1.1 − 1.3) = sigmoid(−0.2) ≈ 0.450

The player wins (outcome = 1). The prediction error is 1 − 0.450 = 0.550:

Δskill_vector = 0.550 × (0.8, 0.6, 0) = (0.440, 0.330, 0) Δdifficulty = −0.550 skill_vector → (1.440, 0.830, 0.2) difficulty → 0.750 # check: new strength = 1.440×0.8 + 0.830×0.6 = 1.650 = 1.1 + 0.550 ✓ # check: Δstrength + Δdifficulty = 0.550 − 0.550 = 0 ✓

The player's skill grew only along this problem's direction, and the problem got easier by exactly the amount the player got stronger.

5. What the skill vector actually is after G games

Unroll the update rule. Starting from zero, after G games on task directions task_direction₁ … task_directionG:

skill_vector = Σ over games i: learning_rate × (outcomeᵢ − expectedᵢ) × task_directionᵢ

The skill vector is literally a weighted sum of the directions of everything the player has played, weighted by how surprising each result was. Three consequences:

  • Transfer is built in. strength on a never-played task = Σ learning_rate(outcomeᵢ − expectedᵢ)(task_directionᵢ · new_task_direction). Beating algebra problems raises your measured strength on calculus exactly in proportion to how aligned the two embeddings are. This is the model's core assumption: skill transfer = embedding similarity. For math this is defensible (skill is g-loaded), but know that you are assuming it.
  • The space fills in slowly. Each game moves the vector along one direction only. With dimension_count = 1536 (attempt-3) and a few hundred games per player, the skill vector is a sparse spray in a vast space. Most of its information lives in far fewer effective dimensions — which is why section 7 recommends truncating the space.
  • The zero point is arbitrary — and the update never re-centers it. If all task directions cluster in one cone (they do — next section), then strength values are all shifted positive, and "zero skill" does not mean "average player". Mean-centering (next section) fixes the origin.

6. Real embedding geometry: anisotropy and the fix

The original text derives the spread of a player's strength over randomly chosen tasks as:

sd(skill_vector · task_direction) = ‖skill_vector‖ / √dimension_count

This is exact if task directions are distributed uniformly over the unit sphere — i.e., if a random problem's direction is as likely to point one way as any other. Attempt-3's matchmaking baked this in:

tolerance = 0.8416 × ‖skill_vector‖ / √1536 # 0.8416 = Φ⁻¹(0.80), the normal quantile
The assumption is false. Real text embeddings are anisotropic: the whole cloud occupies a narrow cone, not the sphere. Measured on a handful of deliberately-unrelated STEM problems (all-MiniLM-L6-v2, see embeddings_writeup.html §5), the mean pairwise cosine between different problems was +0.094 where uniformity predicts 0 — and that was on a corpus designed to be diverse. A real all-STEM corpus sits much deeper in the cone (0.3–0.6 typical). Consequences:
  • strength = skill_vector · task_direction is not zero-mean over tasks — it's shifted positive, so "average" performance is misread as "good".
  • The sd formula understates the spread; tolerance windows computed from it are miscalibrated.
  • Cross-topic transfer is systematically larger than the model intends (everything correlates with everything).
Fix: mean-center the embedding cloud. Compute the corpus mean direction μ over all problem embeddings, subtract it from every problem's vector, and renormalize to unit length. Then "task direction" means "direction away from the average problem" — a much better skill axis ("good at X relative to a typical problem") — and the zero mean assumed by the spread formula is approximately restored. In the measurement cited above, mean-centering moved the mean pairwise cosine from +0.094 to −0.143. Recompute μ whenever problems are bulk-imported; store it alongside the vectors.

7. Choosing the dimension count

Attempt-3 used 1536 dimensions for one reason: that is what OpenAI's text-embedding-3-small emits. That is not a reason. Considerations:

  • Convergence. Each game supplies information along one direction. The more dimensions, the more games are needed before the skill vector is a faithful profile, and the noisier per-axis statistics become. Skill spaces want to be small: on the order of 128–512, not 1536–4096.
  • Effective dimensionality is low anyway. Embedding clouds are not just anisotropic, they are low-rank: in the demo corpus, 6 of 384 principal components carried 90% of the variance (toy scale, but the effect is real and well documented). Extra nominal dimensions were never buying extra skill axes.
  • MRL truncation makes d a free choice. Modern embedding models trained with Matryoshka Representation Learning (Qwen3-Embedding, nomic-embed-text-v1.5, others) are built so that the first N coordinates of the vector form a valid smaller embedding; truncating to 256 dims costs ~1% retrieval quality. So: embed once at the model's native size, store a truncated, renormalized, mean-centered view as the skill space.
  • Search and skills may want different dims. Retrieval quality keeps improving with dims (mildly), skill convergence wants few dims. They can be two projections of the same frozen model's output — but see the versioning warning below.
Recommendation: skill space at 256 dimensions (MRL-truncated, mean-centered, renormalized); search vectors can keep the model's full width. Never mix dimensions or models within one stored column.

8. Cold start

Two cold starts, both broken in attempt-3:

New player: skill_vector = 0

Then strength = 0 on every task and ‖skill_vector‖ = 0, so the tolerance window collapses to a point — the matchmaking band is exactly difficulty ≈ 0. Attempt-3 "fixed" this by commenting out the difficulty filter and hardcoding [-10, 10] "for testing", which shipped. The real fix is an exploration phase: for the first N games, sample problems near the global median difficulty (or uniformly), ignoring the tolerance band, and widen the band smoothly as ‖skill_vector‖ grows from 0. The band formula itself handles the widening once the mean/calibration is right — the problem was only ever the zero vector.

New problem: difficulty is a guess

A problem's difficulty only converges after many attempts (each attempt moves it by at most learning_rate × ½). Seed new problems from their embedding neighborhood: initialize difficulty to the difficulty-weighted average of its nearest few existing problems, then let play refine it. This also makes new problems immediately matchable instead of invisible.

9. Calibrate the matchmaking band empirically

The matchmaking flow (attempt-3, restated): the player's search query is embedded into a query direction; the player's strength is computed against that direction; problems are fetched near the query direction with difficulty inside [strength − tolerance, strength + tolerance], where tolerance targets an 80%/20% win-probability window.

Keep the flow, replace the constant:

  • Do not compute tolerance as 0.8416 × ‖skill_vector‖ / √dimension_count. That derivation assumes isotropic directions (section 6) and a normal strength distribution (unverified).
  • Instead, measure: over the real corpus, compute the distribution of skill_vector · task_direction for the player, and set the band from its empirical quantiles. One extra SQL query over the problems table; no distributional assumptions at all.
  • Recheck the band against realized win rates periodically. If players inside the band win 60% rather than ~50%, widen it; the sigmoid and the band are estimates, the win rate is ground truth.

10. The embedding model is part of the rating state

If you swap or fine-tune the embedding model, every stored skill vector silently changes meaning: the new model's task directions live in a different space, so skill_vector · task_direction_new is noise. Ratings are only valid under the embedding model that produced the task directions.
  • Pin model name + version + dimension count + mean-centering vector version alongside every stored vector. problems.version exists; player skill rows need the same.
  • A model upgrade is a migration: re-embed all problems, recompute μ, and either rescale/archive existing skill vectors or map them through the old→new direction correspondence (lossy; prefer archive + exploration phase, as in cold start).
  • This coupling is the argument for keeping search and skill vectors as separate columns even when they come from the same model: you can retune the search side (truncation, centering, hybrid weights) without touching rating history, as long as the skill projection is frozen.

12. Properties summary (why this design is elegant)

  • One rule, two modes. The same sigmoid + projection update handles player-vs-player and player-vs-problem; the problem is just an opponent whose skill lives on one scalar axis.
  • Reduces to Elo at dimension_count = 1. Nothing special-cased.
  • Zero-sum conservation along the task direction in both modes — rating inflation is structurally contained.
  • Transfer for free: no per-topic rating tables to maintain; generalization falls out of embedding geometry.
  • Difficulty is learned from the population rather than authored, and problems and players are calibrated on the same scale by construction.
